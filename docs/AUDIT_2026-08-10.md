## 2. Findings

### F-1 · The handover documents send the client to a dead URL — **CRITICAL**

`https://inovice-system.vercel.app` returns **404 `DEPLOYMENT_NOT_FOUND`** on
every route. It is not the app's address and, on the evidence, never was.

The live app is **`https://inovice-system-lyart.vercel.app`** — which is what
`.github/workflows/uptime.yml` has been probing all along. That is why uptime
stayed green while the documented URL was dead: *the monitor and the manual
disagree about what production is.*

The wrong hostname appears in four places, and one of them is not a document:

| Location | Consequence |
|---|---|
| `docs/HANDOVER-walkthrough.md:3` | the client's training sheet opens on a 404 |
| `docs/USER-MANUAL.md:9` | every staff member's reference URL is dead |
| `docs/DESIGN_BRIEF.md:7` | cosmetic |
| Supabase Auth `site_url` + `uri_allow_list` (DECISIONS.md:51–52) | stale config, **not currently breaking anything** — see below |

**On the Supabase row — checked, and it is *not* the emergency it looks like.**
D-29 made password reset **code-based (email OTP)**, and the shipped template
`docs/supabase-email-templates/reset-password.html` interpolates only
`{{ .Email }}` and `{{ .Token }}` — no `{{ .ConfirmationURL }}`. Admin user
creation calls `POST /users` with `email_confirm: true` (`lib/auth/admin-api.ts:40`),
so it sends no confirmation link either. **No current auth flow depends on
`site_url`**, which is exactly the resilience D-29 was chosen for.

It is still wrong and should be corrected in Supabase → Authentication → URL
Configuration, because it is a loaded trap for the day anyone enables a
link-based email. Priority: low, not urgent. **⚠ OWNER-VERIFY.**

The critical half of this finding is the documentation: **the client and staff
were about to be handed a dead address.** Docs are fixed in this branch.

### F-2 · Production has no error monitoring — **HIGH · CODE DONE, needs an account**

`@sentry/nextjs` was **not installed**. The only trace of it was a comment in
`app/(shell)/error.tsx`: *"Server log only until Sentry lands (7.2's blocked
half)."* CLAUDE.md §2 mandates Sentry; BUILD_PHASES 7.2 was never completed
because the account was never created.

Net effect: when the app threw in front of a customer, nothing told anyone. The
uptime pinger is not a substitute — it proves the login page returns 200, which
stays true while every invoice issue is failing.

**Wired** (`@sentry/nextjs` 10.69.0):

| File | Role |
|---|---|
| `instrumentation.ts` | server/edge boot + `onRequestError` — the hook that catches uncaught Server Component, route-handler and server-action errors |
| `instrumentation-client.ts` | browser init + router transition instrumentation |
| `sentry.server.config.ts` / `sentry.edge.config.ts` | runtime configs (edge covers `middleware.ts`, the auth gate) |
| `app/global-error.tsx` | **new** — catches failures in the root layout itself, which `app/error.tsx` structurally cannot |
| `app/error.tsx`, `app/(shell)/error.tsx` | now `captureException` as well as logging |
| `next.config.ts` | `withSentryConfig`, `tunnelRoute: "/monitoring"` so ad blockers cannot swallow browser reports |

Decisions worth knowing, given this app holds customer names, TRNs and amounts:

- **`sendDefaultPii: false`** everywhere, and `beforeSend` deletes
  `request.query_string` — the one place a customer or invoice id leaks into a
  URL. The route pattern is what makes an error diagnosable, not the id.
- **Session Replay deliberately not enabled.** It would record invoice screens.
- **`tracesSampleRate: 0.1`.** Errors are the point; full tracing on a 10-user
  internal tool is quota burned for nothing.
- **Inert without a DSN.** `init()` is inside `if (dsn)`, so with the env blank
  there is no network and no overhead. Verified: `pnpm build` passes and
  `next start` serves `/login` at HTTP 200 with the DSN unset.
- `disableLogger` / `automaticVercelMonitors` deliberately **not** set — both
  are deprecated in SDK 10 and webpack-only, and this project builds with
  `--turbopack`, so they would only print warnings.

**Cost:** middleware bundle grows 94 kB → 163 kB (the edge SDK). Well inside
limits, and middleware is the auth gate — its failures are worth seeing.

**Remaining — owner, ~15 minutes, needs credentials this machine does not have:**

1. Create a Sentry account and a project (platform: Next.js).
2. Put the DSN in **Vercel → Settings → Environment Variables** as both
   `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN` (same value), for Production.
   Optionally add `SENTRY_ORG`, `SENTRY_PROJECT`, `SENTRY_AUTH_TOKEN` to get
   readable stack traces instead of minified ones.
3. Redeploy. No code change is required — the wiring activates on the DSN.
4. In Sentry → Alerts, route "a new issue is created" to the operator's email.
   That is 7.7's other half, the one the uptime probe cannot cover.
5. Verify end to end by throwing once from a test route and watching it arrive.

### F-3 · The test suite was aimed at the client's live database — **HIGH · FIXED**

*Amended after implementation — the first write of this finding understated it.*

All 25 `pnpm test:db:*` scripts, plus `db:seed` and `db:reseed`, run
`node --env-file=.env.local`, which now points at the **production** project.

The tests were not unguarded. Each of the 25 carried its own copy of:

```js
const STAGING_REF = "kxtbxgcvwxvlsoygjvvi";
if (!dbUrl?.includes(STAGING_REF)) { refuse }
```

which was right while that project was staging. **At go-live the same project
became production and nobody edited 25 files.** The guard did not stop working —
it inverted. It went from "only run against staging" to "only run against the
client's live ledger", and would have *refused* to run against a safe database.

`scripts/reseed.mjs` — which TRUNCATEs `settings` and re-seeds placeholder
company details — had no ref check of any kind.

**Fixed** in `db/guard.mjs`, a single shared guard replacing all 26 copies. It
fails closed:

- the production ref is refused outright, **with no override** — no flag, no env
  var. Sealed invoices cannot be deleted, so there is no safe "yes I'm sure";
- any other database must be *declared* disposable (`DB_ENV=staging|development|
  test`, or a localhost connection). An unrecognised database is refused,
  because "I don't know what this is" must never resolve to "go ahead";
- read-only and operator tools deliberately do **not** call it — `audit:db`,
  `db:backup`, `db:drill` and `wipe-demo.mjs` are meant to run against
  production and keep their own confirmations.

Verified across six paths: production ref refused; unknown project refused;
`DB_ENV=staging` allowed; localhost allowed; production ref **still** refused
with `DB_ENV=staging` set; and `audit:db` + `wipe-demo` dry run unaffected
(46 passed · 0 failed after the change).

When a real staging project exists again, nothing here needs editing — set
`DB_ENV=staging` in that machine's `.env.local`.

### F-4 · No security headers — **MEDIUM**

`next.config.ts` is an empty config object. Absent: `Content-Security-Policy`,
`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`. Only Vercel's default HSTS is present.

An app that displays sealed financial documents can currently be framed by any
site (clickjacking) and will MIME-sniff responses. This is a ~20-line addition
to `next.config.ts` and the cheapest risk reduction on this list.

`pnpm audit --prod` reports **35 advisories (16 high, 18 moderate, 1 low)**, and
the paths all run through one root: `shadcn@4.13.0 → @modelcontextprotocol/sdk
→ hono`. `shadcn` is a scaffolding CLI used at development time to add
components; it has no business in the runtime dependency tree.

Moving it to `devDependencies` should clear the entire advisory list. Verify
with `pnpm audit --prod` after the move — expect 0.
