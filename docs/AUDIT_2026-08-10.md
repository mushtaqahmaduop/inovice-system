## 2. Findings

### F-1 · The handover documents send the client to a dead URL — **CRITICAL**

`https://inovice-system.vercel.app` returns **404 `DEPLOYMENT_NOT_FOUND`** on
every route. It is not the app's address and, on the evidence, never was.

The live app is **`https://inovice-system-lyart.vercel.app`** — which is what
`.github/workflows/uptime.yml` has been probing all along. That is why uptime
stayed green while the documented URL was dead: *the monitor and the manual
disagree about what production is.*

The wrong hostname appears in four places, and one of them is not a document:

| Location | Consequence |
|---|---|
| `docs/HANDOVER-walkthrough.md:3` | the client's training sheet opens on a 404 |
| `docs/USER-MANUAL.md:9` | every staff member's reference URL is dead |
| `docs/DESIGN_BRIEF.md:7` | cosmetic |
| Supabase Auth `site_url` + `uri_allow_list` (DECISIONS.md:51–52) | stale config, **not currently breaking anything** — see below |

**On the Supabase row — checked, and it is *not* the emergency it looks like.**
D-29 made password reset **code-based (email OTP)**, and the shipped template
`docs/supabase-email-templates/reset-password.html` interpolates only
`{{ .Email }}` and `{{ .Token }}` — no `{{ .ConfirmationURL }}`. Admin user
creation calls `POST /users` with `email_confirm: true` (`lib/auth/admin-api.ts:40`),
so it sends no confirmation link either. **No current auth flow depends on
`site_url`**, which is exactly the resilience D-29 was chosen for.

It is still wrong and should be corrected in Supabase → Authentication → URL
Configuration, because it is a loaded trap for the day anyone enables a
link-based email. Priority: low, not urgent. **⚠ OWNER-VERIFY.**

The critical half of this finding is the documentation: **the client and staff
were about to be handed a dead address.** Docs are fixed in this branch.

### F-2 · Production has no error monitoring — **HIGH**

`@sentry/nextjs` is **not installed**. The only trace of it is a comment in
`app/(shell)/error.tsx`: *"Server log only until Sentry lands (7.2's blocked
half)."* CLAUDE.md §2 mandates Sentry; BUILD_PHASES 7.2 was never completed
because the account was never created.

Net effect: when the app throws in front of a customer, nothing tells anyone.
The operator learns about outages by phone call. For a system that seals legal
documents, that is the gap I would close first after F-1.

The uptime pinger is not a substitute — it proves the login page returns 200,
which stays true while every invoice issue is failing.

### F-3 · The test suite is aimed at the client's live database — **HIGH**

All 25 `pnpm test:db:*` scripts, plus `db:seed` and `db:reseed`, run
`node --env-file=.env.local`. `.env.local` now points `DATABASE_URL` and
`DATABASE_URL_MIGRATIONS` at the **production** Supabase project.

`pnpm db:reseed` against that file would repopulate the ledger you just spent
two sessions clearing, and the write-heavy task tests would mint invoices into
the client's live books — invoices that, once sealed, **cannot be deleted by
design**. The only recovery is another TRUNCATE.

Nothing has gone wrong yet; the loaded gun is simply pointed at production. The
fix is a guard in the test bootstrap that refuses to run against a database
whose host matches production, or a separate `.env.staging.local`.
**Not fixed in this branch — it needs a decision on which shape you want.**

### F-4 · No security headers — **MEDIUM**

`next.config.ts` is an empty config object. Absent: `Content-Security-Policy`,
`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`,
`Permissions-Policy`. Only Vercel's default HSTS is present.

An app that displays sealed financial documents can currently be framed by any
site (clickjacking) and will MIME-sniff responses. This is a ~20-line addition
to `next.config.ts` and the cheapest risk reduction on this list.

### F-5 · `shadcn` is a production dependency — **MEDIUM**

`pnpm audit --prod` reports **35 advisories (16 high, 18 moderate, 1 low)**, and
the paths all run through one root: `shadcn@4.13.0 → @modelcontextprotocol/sdk
→ hono`. `shadcn` is a scaffolding CLI used at development time to add
components; it has no business in the runtime dependency tree.

Moving it to `devDependencies` should clear the entire advisory list. Verify
with `pnpm audit --prod` after the move — expect 0.

### F-6 · The FTA retention copy exists on exactly one laptop — **MEDIUM**

`backups/` holds three files worth keeping (the ledger dump plus two pre-delete
JSONs) and they exist **only** on this machine. Per D-06 the monthly `pg_dump`
to client-owned storage *is* the 5-year retention mechanism — Supabase's daily
backups are disaster recovery measured in days, not the legal retention.

Step 2 of RUNBOOK-backup-restore.md has been open since the runbook was written,
blocked on "which storage is the client's". **That question goes into the client
briefing.** Until it is answered, one disk failure costs the retention copy.

### F-7 · The uptime monitor's real cadence is ~35–120 minutes, not 15 — **LOW**

The cron says `*/15` but observed run times are 04:08, 02:10, 23:49, 23:11,
22:36, 21:52 — GitHub throttles scheduled workflows on free runners. Alerting is
"GitHub emails the repo owner when a scheduled run fails."

That is honest monitoring for a 10-user internal tool and I would not spend
money fixing it — but the handover should not claim 15 minutes when it is closer
to an hour. Corrected in the handover doc in this branch.
