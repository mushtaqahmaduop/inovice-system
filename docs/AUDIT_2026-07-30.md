## 2. Database invariants — `db/tests/audit-readonly.mjs` (new)

**47 passed, 0 failed.** Run with
`node --env-file=.env.local db/tests/audit-readonly.mjs`.

This script is new and deliberately **read-only** — every statement is a SELECT, so it is
safe against any environment including production. It exists because the rest of
`db/tests/*.test.mjs` is **destructive** and hard-guarded to the staging ref, which left no
way to assert the invariants against real data.

Verified:

- **Enforcement layer exists** — the transition guard, payments append-only, and both
  parent-lock triggers; `issue_invoice()`, `void_invoice()`, `delete_draft()` all present,
  all `SECURITY DEFINER`, all with a pinned `search_path`.
- **RLS enabled on all 14 tables.**
- **No `UPDATE`/`DELETE` granted** to `anon`/`authenticated` on `payments`,
  `invoice_events`, `deleted_drafts`.
- **Numbering (§3.2)** — no draft carries a number; every sealed invoice has one; 2026 is
  gapless `1..24`; no duplicate `(number_year, number_seq)`.
- **Sealed money (§3.3)** — `grand_total = govt + service + extras + vat` on every sealed
  invoice; no negative fee anywhere; every sealed invoice carries its VAT + customer
  snapshot.
- **D-30 / D-30a** — `invoice_list.customer_total = grand_total + delivery_fee` on every
  issued invoice; every **draft**'s `delivery_fee` equals the sum of its line cells; every
  **sealed** invoice either matches its lines exactly (issued after 0017) or has lines at 0
  (issued before it). 13 invoices carry delivery, 2,068.00 AED total.
- **Payments ledger** — no zero-amount rows, no orphans, none attached to a draft, none
  reversed twice. 22 payments, 0 reversals.
- **Referential** — no extra fee whose column belongs to another invoice. 18 migrations
  tracked.

The 0017 design is confirmed working end-to-end on data entered through the UI: **INV-19,

invoice figure exactly (600.00 / 500.00 / 50.00). INV-15/16/17, issued yesterday, correctly

## 4. What I did NOT run, and why

**The destructive DB suite** (`db/tests/task-*.test.mjs`, 25 files). These mutate real rows
and are hard-guarded to the staging ref — which `.env.local` currently matches, so they
*would* have run. They would have altered the exact data you have been reviewing on the
preview, including the invoices issued today. Not something to do unattended. They should be
run deliberately, against a database whose contents are disposable.

**A load test.** Three reasons, all real:

1. The preview is SSO-gated, so it cannot be driven without a **protection-bypass token**.
2. It shares the staging Supabase, so load would pollute the data you are reviewing and
   **consume real invoice numbers** — which are gapless and never reused.
3. Meaningful numbers need a disposable database, not the one holding your review data.

The latency figures I could collect (0.44–0.68s) measure Vercel's **SSO redirect**, not the
application, so they say nothing useful about app performance.

**Proposed load-test plan, for approval:**

- Generate a Vercel **Protection Bypass for Automation** token so a script can reach the app.
- Point the deployment at a **throwaway Supabase project** seeded from `db/seed.mjs`.
- Drive it with `autocannon` (or `k6`): read-heavy first (`/dashboard`, `/invoices`,
  `/invoices/[id]`) at 10 → 50 concurrent for 60s; then a **serialised** issue-flow run,
  since `issue_invoice()` row-locks the year counter and concurrent sealing is *supposed* to
  serialise — that is the interesting measurement.
- Watch Supabase pooler saturation: the invoice list reads all issued rows per dashboard
  render, which is the first thing that will hurt as volume grows.
